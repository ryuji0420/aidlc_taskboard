## ストーリー分割アプローチの選択肢（参考）

| アプローチ | 内容 | 利点 | 留意点 |
|------------|------|------|--------|
| **User Journey-Based** | 画面遷移・利用の時間順 | 体験の流れが分かりやすい | 同一画面の複数操作が分散しうる |
| **Feature-Based** | 列管理・カード CRUD・永続化など機能単位 | 実装単位と対応しやすい | ジャーニー横断の整合は別途確認 |
| **Persona-Based** | ペルソナごとにストーリーを束ねる | 利害調整に向く | 小規模だと重複しやすい |
| **Domain-Based** | ドメイン（例: タスク集約・ストレージ）単位 | 境界が明確なとき有効 | 初版の小さめアプリでは過剰になりうる |
| **Epic-Based** | 大項目の下に子ストーリー | ロードマップに向く | 初版単一リリースでは階層が厚くなりうる |

**推奨（提案）**: 初版スコープでは **Feature-Based を主**にし、必要に応じて **User Journey** で 1〜2 本補足するハイブリッド。

### Question 2 — ストーリーの分割方針

初版のストーリーはどの切り方を優先しますか？

A) Feature-Based のみ  
B) User Journey-Based のみ  
C) Feature-Based を主に、導入ジャーニー用に 1 本だけ User Journey 系を追加

[Answer]: **C（ハイブリッド）** — ユーザーが「Question 2 補足」で **パターン C** を明示（チャット）

#### Question 2 補足 — 分割方針の具体例（TaskBoard Mini 向け）

同じ「初版 MVP」でも、ストーリーの切り方は次のように変わります。

**パターン A — Feature-Based のみ（機能単位）**

| 例となるストーリー名（案） | ざっくり内容 |
|---------------------------|--------------|
| 列を複数表示する | To Do / Doing / Done 等、複数列が画面上に並ぶ |
| 列を管理する | 列の追加・名称変更・削除（実装方針に沿う） |
| カードを追加する | 列を選び／既定列に、タイトル付きカードを追加 |
| カードを編集する | タイトル等の編集 |
| カードを削除する | 1 枚のカードを除去 |
| ボード状態を永続化する | 再読込後も同じ列・カードが復元される |

**パターン B — User Journey-Based のみ（利用の流れ）**

| 例となるストーリー名（案） | ざっくり内容 |
|---------------------------|--------------|
| 初めてボードを開く | 初回表示・空または既定列 |
| 最初のタスクを登録する | 入力からカード出現まで |
| 作業中のタスクを更新する | 編集の流れ |
| 終わったタスクを片付ける | 削除または列移動（※D&D はスコープ外のため「操作の流れ」としては編集・削除中心） |
| 翌日も続きから使う | 永続化の体験 |

**パターン C — ハイブリッド（Epic 1 本 + Feature 主 + ジャーニー補助）**

- **Epic**: 「MVP タスクボード」（Question 5-B に合わせ 1 段階の Epic）
- **子ストーリー**: 主に **パターン A** のように列・カード・永続化へ分割（Question 4-A の細かめに合う）
- **任意**: 受け入れテストの文脈で「初回訪問から最初のカード追加まで」など **ジャーニー 1 本**を補助的に書く（必須ではない）

#### 本プロジェクトでの確定方針（Question 2 の解消）

- Question **4: A（細かめ）**、Question **5: B（Epic 1 段）** と整合させると、**パターン C** が最も説明しやすいです。  
- すなわち **Epic「MVP タスクボード」配下に、Feature ベースで細かいユーザーストーリーを複数置く**。ジャーニーは AC の補足として必要なら 1 本まで。

Part 2 の `stories.md` ではこの方針で生成する。
