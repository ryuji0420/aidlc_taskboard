### Question 6 補足 — プロパティベーステスト（PBT）とは何か

**ざっくり言うと**: 「決め打ちの例だけ」ではなく、**ランダムに生成した大量の入力**に対して、「常に成り立つはずの性質（プロパティ）」が崩れていないかを自動で確かめるテストの書き方・運用ルールのことです。AI-DLC の PBT 拡張は「その方針をプロジェクトの**必須ルール**にするか」を聞いています。

| 普通の単体テスト（例） | プロパティベーステスト（イメージ） |
|------------------------|-----------------------------------|
| 「`add(2,3)` の結果は `5`」と 1 ケースだけ書く | 「**任意の**整数 `a, b` で `add(a,b) === add(b,a)`」のように、**入力のクラス全体**に対するルールを書き、ツールがランダム入力を何百回も試す |

**タスクボードに当てはめた具体例**（あくまでイメージ）:

- **シリアライズの往復**: ボードの状態を `localStorage` 用の JSON 文字列にし、また読み戻す。**保存前後でカード枚数や ID の集合が変わらない**、などをプロパティとして書く。  
- **並べ替え・移動のルール**: 「カードを列に追加した直後、その列のタスク ID にそのカードが含まれる」など、**操作のあと必ず真になる条件**をランダムな操作列で検証する（実装が複雑になるほど PBT の効きやすい領域）。  
- **純粋関数だけに Partial**: 例えば「期限の表示用ラベルを返す関数」「ソートキーを計算する関数」など、**同じ入力なら必ず同じ出力**の関数だけに PBT を当てる、という切り方。

**選択肢の目安**:

- **A (Yes)**: 状態遷移・変換・保存形式など、**ロジックを広く** PBT で縛りたい（ルール上も「未実施は NG」になりやすい）。  
- **B (Partial)**: **保存／読込の往復**と、**純粋関数**にだけ PBT を適用し、UI の細部までは求めない。  
- **C (No)**: 初版が **列＋カードの CRUD とブラウザ保存中心**で、複雑な不変条件をランダム検証までルール化しない（手書きの単体／結合テストや手動確認で十分とする）。  

本プロジェクトの現時点の回答（静的ホスト・Vue・ブラウザ保存・列とカードの基本操作のみ）だけを見ると、**C または B** が現実的なことが多いですが、最終判断はチームの品質方針に合わせてください。
